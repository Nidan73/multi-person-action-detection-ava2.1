PROMPT ENGINEERING RULES YOU MUST FOLLOW
When I ask you to write a prompt or review one, apply these rules:

CONTEXT COMPLETENESS

every variable the target AI needs must be explicitly stated

file paths, tensor shapes, class names, function signatures

if something was verified on my machine, say so and give the
exact values

do NOT leave blanks for the target AI to guess

ANTI-ASSUMPTION RULES

if the target AI might assume a wrong default, explicitly say
"DO NOT assume X, the correct value is Y"

if a library API has multiple ways to do something and the
target AI might pick the wrong one, specify exactly which
method to use

if a value was verified empirically (like feature map shape),
say "VERIFIED ON MY MACHINE, hardcode this"

CONTEXT WINDOW MANAGEMENT

estimate input + output tokens before sending

if total likely exceeds safe limits, propose a split

typical safe output per response: ~4000-8000 tokens

a complex Python file with 300+ lines = ~4000-6000 tokens

asking for 4+ complex files in one response = almost
certainly too much

rule of thumb: one complex file per prompt, or 2-3 simple
files per prompt

OVERTHINKING PREVENTION

if the prompt requires the AI to figure out library internals
(e.g., "how does YOLO batch inference work?" or "what is the
exact feature map shape of X3D-XS?"), this WILL cause loops

solution: run a diagnostic script first, get the answer,
hardcode it in the prompt

always prefer "here is the verified answer, use it" over
"figure this out yourself"

OUTPUT FORMAT CONTROL

always specify the exact output structure you want

"respond in this order: A, B, C, D"

"give me the complete file, do not truncate"

"do NOT generate code in this response, design only"

separating design from code generation is critical for
complex tasks

SCOPE CONTROL

explicitly say what NOT to do

"do NOT generate training loop yet"

"do NOT rewrite my preprocessing"

"do NOT use detectron2"

negative constraints prevent scope creep

SPLIT STRATEGY
When a task is too big, the standard split pattern is:

Prompt A: design decisions only, no code

Prompt B: first code file

Prompt C: second code file

Prompt D: verification / testing code
Each prompt carries forward context from previous responses.

VERIFICATION BEFORE PROCEEDING

after each code generation, require a smoke test

do NOT proceed to the next file until the current one passes

this prevents cascading errors

PROMPT STRUCTURE TEMPLATE
Good prompts for code generation follow this pattern:
a) role + behavior instructions
b) project context (what exists, what is verified)
c) exact task (what to generate)
d) technical specifications (shapes, paths, APIs)
e) constraints (what NOT to do)
f) output format (exact order of response sections)
g) verification criteria (how to test the output)

LESSONS LEARNED FROM THIS PROJECT
These specific failure modes happened in this project:

asking for 4 Python files in one prompt → output truncated

asking AI to figure out YOLO batching API → 10-minute
overthinking loop then crash

asking AI to determine X3D-XS feature shape → 20+ loops
on architecture tracing then crash

using index 3 instead of 4 for center frame → caught by
prompt review, would have caused silent mAP degradation

not specifying exact detector choice → AI picks something
incompatible with Windows

not estimating processing time → user surprised by 90-min
pipeline run

argparse boolean parsing bug with from __future__ import annotations → requires string type checking ft = f.type if isinstance(f.type, str) else f.type.__name__

AI hallucinating dataset caching bugs when seeing 68s vs 10s epoch times on Windows → this is normal spawn + CUDA + OS page cache overhead. Do NOT try to "fix" the dataloader.

Apply these lessons to ALL future prompts.

then head
